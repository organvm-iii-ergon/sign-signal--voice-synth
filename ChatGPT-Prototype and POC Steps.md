# Speech-Score Composition System

## Screen-by-Screen POC Build Spec

### Document ID
`$SPEECH_SCORE_ENGINE__POC_BUILD_SPEC__BAKERY_DEMO__v0_1`

### Purpose
This document defines the first functional proof-of-concept for the Speech-Score Composition System. It is intentionally narrow. It proves that a user can move from dramatic text to audible, revisable, shareable performance-time inside one browser-based workflow.

The POC is not the full speech-score engine. It is the smallest serious product artifact that demonstrates the listening-and-revision loop.

### Governing proposition
A playwright, dramaturg, director, teacher, or performance-maker can paste a scene, verify parsing, assign voices, hear the scene, inspect weak points, revise against sound, save a version, and share a read-only review artifact.

### Timing and sequencing requirement
Tracker-like time and sequence behavior is a core product requirement, not an optional later embellishment.

The system must treat dialogue as discrete timed events moving through a deterministic sequence model rather than as a loose continuous text stream. Even in this first POC, playback logic should be conceived in tracker terms: ordered event rows, explicit event boundaries, deterministic replay, stable timing offsets, and region-based repetition. The POC does not yet need full `$PATTERN_VIEW`, but its playback engine, line model, and selection-replay behavior must be compatible with that future. The build should therefore avoid any architecture that assumes only paragraph-style document playback.

### POC scope
This POC includes exactly four primary screens:

1. `$SCREEN_01_NEW_SCENE_IMPORT`
2. `$SCREEN_02_PARSE_REVIEW`
3. `$SCREEN_03_SCENE_WORKSPACE`
4. `$SCREEN_04_SHARE_VIEW`

Version save, diagnostics, and speaker controls may appear as subpanels or overlays inside the workspace rather than as separate full screens.

### Out of scope
True simultaneous overlap composition, visual score editing, conductor tooling, collaboration-presence features, institutional administration, and advanced acting controls are explicitly deferred.

---

## 1. Success Criteria

The POC succeeds if a first-time user can complete the following loop without instruction:

Paste or load the bakery scene. Parse it. Correct any speaker issues. Press play. Hear synchronized playback. Adjust pace or voices. Replay a selected region. Inspect one or more diagnostic findings. Save a version. Generate a read-only share link.

A second-order success condition is that the artifact feels like a working development tool rather than a static mockup.

## 2. Canonical Demo Content

### 2.1 Demo scene title
`Philip Glass Buys a Loaf of Bread — Bakery Demo`

### 2.2 Demo purpose
This sample scene demonstrates the product at two levels simultaneously.

At the surface level, it behaves like ordinary dialogue and proves the listening-first revision workflow.

At the deeper level, it hints at the system’s long-range trajectory toward repetition, redistribution, rhythmic intensification, and speech-as-score.

### 2.3 Demo speaker set
`FIRST_WOMAN`

`SECOND_WOMAN`

`GLASS`

`BAKER`

Optional narrator handling for stage directions:

`NARRATOR` or `STAGE_DIRECTION` as a toggled non-character voice-channel.

### 2.4 Demo input text
The POC should preload the scene in the following simplified import format:

```text
TITLE: Philip Glass Buys a Loaf of Bread — Bakery Demo

[STAGE_DIRECTION] A bakery counter with a bakery case below it. Behind the glass of the bakery case, a single loaf of bread on a shelf. A large clock high up on the wall, stopped at 12:01. A sign that says NO CHANGE. A door to the outside, with a bell over it.

[STAGE_DIRECTION] At lights up: A BAKER is behind the counter, smiling. PHILIP GLASS is before the counter. Quite serious, TWO WOMEN are at the door of the bakery, about to go out. THE FIRST WOMAN is looking back at PHILIP GLASS. The SECOND WOMAN is looking away. The BAKER and PHILIP GLASS form one distinct area, the TWO WOMEN another, separate from them. They all remain like that, very still for a moment.

FIRST_WOMAN: Isn’t that Philip Glass?
SECOND_WOMAN: I think it is.
BAKER: Can I help you, sir?
GLASS: Yes. I need a loaf of bread, please.
BAKER: Just a moment.
FIRST_WOMAN: It’s time now.
SECOND_WOMAN: Yes. Let’s go.
BAKER: Do you know that woman, sir?

[STAGE_DIRECTION] A bell rings.
```

### 2.5 Demo version states
The POC should ship with three internal demo version presets.

`$VERSION_A__BASE_READ`
The straightforward imported scene.

`$VERSION_B__PACE_SHIFT`
A version with slightly faster global pace and shorter pauses.

`$VERSION_C__HEIGHTENED_RENDER`
A version with different voice assignments and a slightly stronger contrast between speakers.

These versions let the team prove versioning, comparison logic, and interpretation changes without needing user-generated history on day one.

## 3. Shared Interaction Principles

### 3.1 Speed over ornament
Every screen should privilege immediate action.

### 3.2 Trust through inspectability
Whenever the system makes an inference, the user must be able to see and correct it.

### 3.3 Temporal legibility
Playback, line focus, and diagnostics must all point back to time.

### 3.4 Sequence determinism
The POC must preserve deterministic event order. A selected passage should replay identically under the same settings state. Timing changes must come from explicit controls such as global pace, pause-after-line, or speaker pacing offsets rather than from hidden or unstable behavior.

### 3.5 Tracker compatibility
Although the interface remains document-legible, the internal timing model should already map cleanly onto future tracker-style sequencing. In practice, each spoken unit should behave like a bounded event with ordered position, speaker assignment, duration estimate, and replay eligibility.

### 3.6 One-screen working center
The workspace is the product center of gravity.

### 3.7 Read-only means read-only
The share artifact must not expose editing behavior.

## 4. Screen 01 — New Scene Import

### 4.1 Canonical identifier
`$SCREEN_01_NEW_SCENE_IMPORT`

### 4.2 Functional purpose
Allow a user to begin from blank text or from the bakery sample and move into parsing with minimal friction.

### 4.3 Primary user question
“How do I get a scene into the system fast?”

### 4.4 Layout model
The screen is a two-column layout.

The left two-thirds contain the scene creation form and text import area.

The right one-third contains simple formatting guidance, a bakery sample card, and a short explanation of what the parser expects.

### 4.5 Required visible regions
A top bar with product name and lightweight navigation.

A scene metadata strip containing title and optional project selector.

A large text entry area for paste or typed dialogue.

A right-side help panel.

A footer action row with primary and secondary actions.

### 4.6 Required components
`$FIELD_SCENE_TITLE`
Plain text input. Default value when loading sample: `Philip Glass Buys a Loaf of Bread — Bakery Demo`.

`$FIELD_PROJECT`
Optional lightweight selector. May default to `Demo Project` in POC.

`$FIELD_RAW_TEXT`
Large text area supporting paste, keyboard entry, and sample insertion.

`$CARD_SAMPLE_SCENE`
Prominent card labeled `Load Bakery Demo`.

`$PANEL_FORMAT_HINTS`
Shows the accepted convention:

```text
SPEAKER: line of dialogue
[STAGE_DIRECTION] descriptive text
```

`$ACTION_PARSE_SCENE`
Primary call-to-action.

`$ACTION_LOAD_SAMPLE`
Secondary call-to-action that fills title and text automatically.

`$ACTION_CLEAR`
Resets the form.

### 4.7 Default screen state
The right-side sample card is visible immediately.

The text area contains placeholder formatting hints, not actual content.

The parse button remains disabled until the title and some body text exist.

### 4.8 Primary interactions
When the user presses `Load Bakery Demo`, the title field and raw text area populate instantly.

When the user presses `Parse Scene`, the system sends raw text to parsing and routes to parse review.

### 4.9 Validation rules
Empty title blocks forward motion.

Empty text blocks forward motion.

The parser should tolerate imperfect formatting; it should not reject lightly malformed text.

### 4.10 Loading and error states
While parsing, the primary button changes to `Parsing…` and shows progress feedback.

If parsing fails, keep the user on the screen and show a plain-language recovery message.

### 4.11 UX annotation
This screen must feel forgiving, not formalistic. It should tell the user that the system can work with ordinary dramatic text and that any mistakes can be corrected on the next screen.

### 4.12 Acceptance criteria
A user can load the bakery sample and reach parse review in one action.

A user can paste a manually formatted scene and reach parse review in under one minute.

## 5. Screen 02 — Parse Review

### 5.1 Canonical identifier
`$SCREEN_02_PARSE_REVIEW`

### 5.2 Functional purpose
Let the user verify speaker detection, stage-direction classification, and line segmentation before entering the workspace.

### 5.3 Primary user question
“Did the system interpret my scene correctly?”

### 5.4 Layout model
The screen is a two-column inspection layout.

The left column shows raw imported text.

The right column shows structured parsed output grouped by speaker.

A slim action bar sits at top with `Back`, `Continue to Workspace`, and parse status summary.

### 5.5 Required visible regions
Top action bar.

Left raw text review panel.

Right parsed scene structure panel.

Bottom summary strip with counts.

### 5.6 Required components
`$PANEL_RAW_TEXT`
Scrollable display of the imported scene.

`$PANEL_PARSED_LINES`
Shows each parsed unit with speaker label, line content, and type.

`$CHIP_SPEAKERS`
Visible set for `FIRST_WOMAN`, `SECOND_WOMAN`, `GLASS`, `BAKER`, and optional `STAGE_DIRECTION`.

`$CONTROL_RENAME_SPEAKER`
Inline rename for ambiguous labels.

`$CONTROL_MERGE_SPEAKERS`
Used if duplicate forms appear.

`$CONTROL_MARK_STAGE_DIRECTION`
Allows converting a parsed line to stage direction.

`$CONTROL_MARK_SPOKEN_LINE`
Allows converting stage direction back to spoken line.

`$SUMMARY_PARSE_COUNTS`
Displays spoken line count, speaker count, and stage-direction count.

`$ACTION_CONTINUE_TO_WORKSPACE`
Primary forward action.

### 5.7 Default parsed bakery state
The parser should produce:

`FIRST_WOMAN` with two spoken lines.

`SECOND_WOMAN` with two spoken lines.

`GLASS` with one spoken line.

`BAKER` with three spoken lines.

Two stage-direction blocks and one bell event stage direction.

### 5.8 Primary interactions
The user can rename labels directly.

The user can merge or split speaker identities if needed.

The user can toggle stage-direction handling.

The user can continue once every spoken line is assigned to exactly one speaker.

### 5.9 Validation rules
Every spoken line must belong to one speaker.

At least one speaker must exist.

Stage directions may exist without a narrator voice assignment at this stage.

### 5.10 UX annotation
This is the product’s first trust test. The system should feel inspectable and correctable, never opaque.

### 5.11 Acceptance criteria
The bakery sample arrives correctly parsed with zero required corrections.

A user can repair a bad parse without returning to the import screen.

## 6. Screen 03 — Scene Workspace

### 6.1 Canonical identifier
`$SCREEN_03_SCENE_WORKSPACE`

### 6.2 Functional purpose
Serve as the main authoring, listening, revision, diagnostics, and versioning environment.

### 6.3 Primary user question
“Can I hear, inspect, revise, and stabilize this scene here without leaving?”

### 6.4 Layout model
The workspace is a three-pane layout with a persistent top toolbar.

The left pane is the script editor.

The center pane is playback and synchronized focus.

The right pane is a tabbed contextual panel containing speakers, diagnostics, and versions.

### 6.5 Top toolbar
The toolbar contains:

`$SCENE_TITLE`

`$RENDER_STATUS`

`$ACTION_SAVE_VERSION`

`$ACTION_GENERATE_SHARE_LINK`

`$ACTION_COMPARE_DEMO_VERSION` if enabled in POC

### 6.6 Left pane — Script editor region
The editor displays speaker-prefixed lines and stage directions in a readable working format.

Each displayed line should correspond internally to a discrete event row, even if the user does not yet see explicit tracker numbering. The POC may expose lightweight row indices or event numbers to reinforce that the scene is being sequenced rather than merely displayed as prose.

Each line has:

speaker label,
text content,
line number,
optional estimated duration,
selection affordance.

Selected lines should support region replay.

### 6.7 Center pane — Playback region
The playback region contains:

transport controls,
progress bar or scrubber,
current line highlight,
selected region replay,
global pace control,
default pause-after-line control,
scene duration estimate,
optional waveform placeholder if available,
and visible sequence logic sufficient to imply tracker-style temporal organization.

The center pane should be designed as the seed of a later tracker-compatible transport model. Region replay should behave like pattern or phrase replay. Selection should be time-bounded and deterministic. Stepping through adjacent spoken units should feel like stepping through ordered events, not scrolling through inert dialogue.

### 6.8 Right pane — Context tabs
The right pane has three tabs.

#### `$TAB_SPEAKERS`
Shows speaker rows with rename, reorder, voice selector, preview button, and pace offset.

#### `$TAB_DIAGNOSTICS`
Shows summary metrics and clickable findings.

#### `$TAB_VERSIONS`
Shows saved versions, timestamps, duration estimates, and share actions.

### 6.9 Required components
`$EDITOR_SCRIPT_TEXT`
Editable scene body.

`$TRANSPORT_PLAY`

`$TRANSPORT_PAUSE`

`$TRANSPORT_STOP`

`$TRANSPORT_SCRUB`

`$ACTION_REPLAY_SELECTED_RANGE`

`$CONTROL_GLOBAL_PACE`
Range control, default 1.0.

`$CONTROL_DEFAULT_PAUSE_AFTER_LINE`
Simple stepper or slider.

`$LIST_SPEAKERS`
Shows `FIRST_WOMAN`, `SECOND_WOMAN`, `GLASS`, `BAKER`, and optional narrator.

`$VOICE_SELECTOR`
One per speaker.

`$VOICE_PREVIEW`
One per speaker.

`$SUMMARY_DIAGNOSTICS`
At minimum:
scene duration,
lines per speaker,
longest uninterrupted run,
alternation density,
repetition density.

`$LIST_DIAGNOSTIC_FLAGS`
Clickable items returning user to relevant line ranges.

`$LIST_VERSIONS`
Saved states including demo presets.

### 6.10 Bakery demo default speaker settings
`FIRST_WOMAN` → voice profile A, medium-neutral, slightly brisk.

`SECOND_WOMAN` → voice profile B, lower energy, slightly slower.

`GLASS` → voice profile C, measured, neutral pace.

`BAKER` → voice profile D, direct, slightly warm.

Optional `STAGE_DIRECTION` narrator → muted by default.

### 6.11 Bakery demo diagnostic defaults
The POC should precompute a lightweight diagnostics state for the bakery sample.

It may include:

`possible low alternation density in opening stage direction`

`single-line centrality for GLASS`

`possible emphasis point near “It’s time now.”`

`short scene / rapid audition candidate`

The diagnostics should remain pragmatic, not over-interpreted.

### 6.12 Workspace user flows

#### `$FLOW_STEP_THROUGH_SEQUENCE`
The user advances through the scene one event at a time and can replay the current event or a bounded range. This is a minimal proof that the system’s temporal model is sequenced and inspectable rather than purely document-based.

#### `$FLOW_LOOP_SELECTED_RANGE`
The user selects a small passage and loops it repeatedly while changing pace or voice settings. This establishes the tracker-derived idea that a bounded phrase region can be auditioned as a stable timing object.

#### `$FLOW_PLAY_FULL_SCENE`
Press play. Hear the entire bakery scene. Watch synchronized line highlighting.

#### `$FLOW_REPLAY_REGION`
Select `FIRST_WOMAN` through `GLASS`. Replay only that passage.

#### `$FLOW_ADJUST_PACE`
Move the global pace slider. Replay. Confirm changed scene feel.

#### `$FLOW_SWAP_VOICE`
Change `GLASS` or `BAKER` voice profile. Replay a selected region.

#### `$FLOW_EDIT_AND_SAVE_VERSION`
Edit one or more lines, save a version, and replay.

#### `$FLOW_JUMP_FROM_DIAGNOSTIC`
Click a diagnostic flag and jump to the implicated line range.

### 6.13 Versioning behavior
The workspace must preserve the distinction between mutable scene state and immutable saved versions.

A save action creates a named or timestamped version.

The current draft remains editable.

The share link must always point to a version, not to unstable current draft state.

### 6.14 Empty and loading states
If no render exists yet, the playback region shows `Generate first read`.

When a render is pending, show visible `rendering…` feedback without blocking editing.

If diagnostics are not yet available, show `Generate diagnostics` or auto-run after first render.

### 6.15 UX annotation
This screen is the product. The user should be able to edit, hear, diagnose, version, and share without navigation churn.

### 6.16 Acceptance criteria
A user can move from first playback to revised playback without leaving the screen.

A user can save a version and produce a share link from this screen.

A diagnostic flag can send the user directly back to a line or region for replay.

## 7. Screen 04 — Share View

### 7.1 Canonical identifier
`$SCREEN_04_SHARE_VIEW`

### 7.2 Functional purpose
Present a stable, read-only review artifact for collaborators.

### 7.3 Primary user question
“Can I send this to someone so they can hear and review the scene without needing the full product?”

### 7.4 Layout model
A clean centered review layout.

Title at top.

Audio player directly below.

Script text below the player.

Optional collapsible diagnostics summary below the text.

Owner note or version metadata at the bottom.

### 7.5 Required components
`$HEADER_SCENE_TITLE`

`$META_VERSION_LABEL`

`$META_CREATED_AT`

`$PLAYER_READ_ONLY`
Playback only. No editing.

`$SCRIPT_VIEW_READ_ONLY`
Speaker labels and text.

`$DIAGNOSTICS_SUMMARY_COLLAPSIBLE`
Optional.

`$OWNER_NOTE`
Optional sharer note.

`$META_EXPIRATION`
If link expiration exists.

### 7.6 Share behavior
The view must be read-only.

It must resolve to a specific immutable version.

It may permit playback of the full scene and selected highlighted ranges if range support is inexpensive.

It should not require the reviewer to sign in for private review unless access policy demands it.

### 7.7 Bakery demo share default
The POC should allow creation of a share link for `VERSION_A__BASE_READ` and optionally the other demo versions.

The share artifact should display the bakery scene title, audio playback, speaker-attributed script text, and a small diagnostics summary.

### 7.8 UX annotation
This should feel elegant and stable. It is not a public publishing surface. It is a private development instrument.

### 7.9 Acceptance criteria
A reviewer can open the link and understand the artifact immediately.

The reviewer can hear the scene and read it without account creation.

No editing affordance appears.

This POC should not attempt to prove the entire future speech-score ontology.

It should prove the narrow commercial wedge cleanly:

A user can hear dialogue as performed time, revise against that hearing, stabilize versions, and share a private review artifact.
